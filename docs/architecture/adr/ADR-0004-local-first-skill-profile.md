# ADR-0004：个人技能画像只存浏览器 IndexedDB，不建 `edu_user_profile` 表

## 状态（Status）

已接受（Accepted）。2026-11-12。跨设备端到端加密同步**明确延后**，复评条件见本文最后一节。

## 背景（Context）

技能画像包含三类数据，敏感性完全不同：

| 数据 | 来源 | 性质 |
|---|---|---|
| 公共技能标签、课程 × 技能关联度 | `edu_skill_tag`、`edu_course_competency` | **公共数据**，学院能力池与课程分析产出，人人可见 |
| 由已修课程聚合出的技能得分 | `edu_course_record` 命中关联度后加权 | **派生数据**，可从服务端事实重算 |
| 自评等级、私人笔记、职业意向 | 学生自己填 | **私人数据**，学校没有、也不需要 |

方案在三个地方对此有明确要求：

- ch.6.1：「用户私人技能画像默认不存在 `edu_user_profile` 明文表；本地数据与学校正式成绩应严格区分。」
- ch.7.3：「个人画像通过 Dexie.js 存储于 IndexedDB，支持导出与恢复；提示浏览器清理数据风险。」
- ch.7.3：「跨设备『端到端加密同步』必须先评审密钥生成、丢失恢复、冲突合并和威胁模型，再单独上线。」

`V1__edu_schema.sql` 末尾用注释把这条约束钉在了代码里：

```sql
-- 注意：本方案刻意不创建 edu_user_profile 明文表。
-- 个人技能画像默认只保存在浏览器 IndexedDB（Dexie.js），
-- 详见 docs/architecture/adr/ADR-0004-local-first-skill-profile.md。
```

要解决的问题是：**第三类数据存哪里**。存服务端需要一整套加密、字段级授权、导出审计、
删除请求流程；存浏览器则要承担「换个设备就没了」的产品后果。

## 决策（Decision）

1. **私人画像只写浏览器 IndexedDB**，通过 Dexie.js 访问，封装在约定路径
   `frontend/src/utils/education/skillProfileDb.ts`（依赖 `dexie ^4.0.11`，见
   [`versions.md`](../../../versions.md) §3）。
2. **服务端不建 `edu_user_profile` 表**，也不新建任何等价的明文表。
   服务端只提供两个公共接口：
   - `GET /edu/analytics/competency-pool`（学院能力池，数据源 `edu_skill_tag` + `edu_course_competency`）
   - `GET /edu/analytics/course-competency?courseId=`（单门课程的技能关联明细）
3. **「由课程推导的得分」每次现算，不落库**：`GET /edu/analytics/skill-profile` 按当前学生
   的 `edu_course_record` 命中 `edu_course_competency` 做加权聚合，返回
   `score` / `courseCount` / `rationale`。前端把它与本地自评**在客户端合并**后展示，
   不把合并结果回传。
4. **导出 / 导入作为一等功能**，菜单按钮权限 `edu:skill:export`（`V2__edu_permissions.sql`
   的 `menu_id=2071`「画像导出」）。导出为单个 JSON 文件，由浏览器本地生成并下载；
   导入时做 schema 版本检查与条目校验。实现用前端已有的 `file-saver 2.0.5`
   （见 `frontend/package.json`），不引入新的上传接口。
5. **本地库需要显式版本化**：Dexie 的 `version(n).stores({...})` 必须随数据结构变更递增，
   升级钩子里做字段迁移；导出文件里写入 `schemaVersion`，导入低版本文件时先迁移再写。
6. **跨设备端到端加密同步不在本期**。在 `edu_sso_identity` 与 SSO 都落地之前，
   没有可靠的身份锚点，做同步只会把「账号被冒用」升级成「画像被冒用」。

### 本地数据边界（哪张表只属于浏览器）

| 存储 | 数据 | 谁可以读 |
|---|---|---|
| 服务端 `edu_skill_tag` / `edu_course_competency` | 公共标签与课程关联度 | 所有登录用户 |
| 服务端 `edu_course_record` | 本人已修课程与成绩 | 本人 + 有权限的教师/管理员 |
| 服务端 `GET /edu/analytics/skill-profile` 的响应 | 由本人成绩现算的聚合分 | 只有本人（不落库） |
| 浏览器 IndexedDB | 自评等级、私人笔记、职业意向、画像快照 | 只有该浏览器上的该用户 |

不允许出现「IndexedDB 的数据被同步到服务端」的中间态：一旦有服务端副本，
就必须按服务端数据处理（审计、删除请求、脱敏、备份），本 ADR 的结论随之失效。

## 后果（Consequences）

**正面**

- 服务端零隐私存量：泄露数据库不会泄露任何自评、笔记、职业意向。
- 没有「删除个人数据」的实现负担 —— 学生清除站点数据即完成删除。
- 画像可以离线查看与编辑（已从服务端取到的公共数据可缓存），符合「本地优先」的定位。
- 导出文件是纯文本 JSON，学生自己就能检查、备份、迁移。

**需要承担的代价（必须被产品与 UI 显式吸收）**

| 代价 | 缓解措施 |
|---|---|
| **清浏览器数据 / 换设备即丢失** | 技能画像页首屏放置风险提示；提供「导出备份」按钮（`edu:skill:export`）；提示文案必须说明「换设备需先导出再导入」，不能只说「请及时备份」 |
| **同一用户多浏览器数据不一致** | 明确告知「画像属于当前浏览器」；不做隐式合并；导入是**覆盖**而不是增量合并，导入前提示将覆盖本地数据 |
| 教师与管理员看不到学生自评 | 这是产品边界而不是缺陷。教师端只能看到由成绩推导的报告（`edu:analytics:view`），不得设计「查看学生自评」的页面 |
| 无法做服务端统计（例如「全院自评分布」） | 明确排除。若产品后续需要，只能加「匿名上报聚合值」的新 ADR，不能顺手把原始数据上传 |
| 备份文件含隐私 | 导出文件名不带学号姓名；导入前提示「备份文件包含个人记录，请勿上传到公开位置」 |
| 依赖浏览器配额 | IndexedDB 容量足够（画像量级是 KB），但极端配额不足时要捕获异常并提示导出 |
| `dexie` 进入前端依赖树 | 已加入 `frontend/package.json`（`dexie ^4.0.11`，与 `versions.md` §3 一致）；未来升级 Dexie 要连带回归 `skillProfileDb.ts` 的 `version(n).stores()` 迁移 |

## 后续复评清单：跨设备端到端加密同步

只有在**四项都有书面答案**、且通过安全评审之后，才能开写同步功能。
以下每一条都是「必须先回答的问题」，不是实现步骤。

### 1. 密钥生成（Key generation）

- 用什么派生？用户口令 → KDF（Argon2id / PBKDF2-HMAC-SHA256，迭代次数与内存参数写死并版本化），
  还是 WebCrypto 生成的 ECDH P-256 密钥对？
- 密钥存哪里？IndexedDB（可被同源脚本读取）还是不可导出的 `CryptoKey`（刷新后如何恢复）？
- 多设备如何拿到同一把密钥？恢复短语（BIP39 之类的助记词）？二维码？还是第二设备输入一次性码？
- 密钥轮换与版本号：换了密钥后旧密文怎么办（保留旧密钥解密 + 重新加密）？
- 口令遗忘时的行为必须明确定义为「不可恢复」还是「有恢复路径」。二者的产品文案完全不同。

### 2. 丢失恢复（Loss recovery）

- 设备丢失 + 无备份 → 是否接受「数据不可恢复」？谁向学生说明？
- 恢复短语丢失但设备还在 → 能否在设备上重新导出？
- 服务端是否需要保管「加密后的密钥材料」？如果保管，服务端被入侵时是否仍安全？
- 客服/管理员能否帮学生恢复？正确答案应当是**不能**，并且这句话要写进帮助文档。
- 账号被停用/删除时，本地数据与云端密文分别如何处理？

### 3. 冲突合并（Conflict merge）

- 同一标签在两台设备上分别自评 3 分与 5 分，合并结果是什么规则：`updated_at` 的 LWW、
  逐字段合并、还是按设备保留两条并要求用户选择？
- 删除如何同步（tombstone 还是版本向量）？「A 设备删除、B 设备修改」谁赢？
- 时钟不可信（设备时间被改）时 LWW 会出错，是否引入逻辑时钟或服务端序列号？
- 本地 schema 升级与云端旧版本数据并存时的迁移顺序？
- 合并冲突的用户可见性：静默 LWW 还是提示「有两条记录冲突」？

### 4. 威胁模型（Threat model）

- 服务端被完全入侵时，攻击者能得到什么？必须只有：密文、条目数量、大小、时间戳。
  任何明文元数据（标签名、笔记长度分布）都要在文档里列出并评估。
- 同源 XSS 能读到 IndexedDB 与内存中的密钥。CSP、依赖审计、`innerHTML` 禁令是否到位？
- 浏览器扩展、共享设备、公用机房电脑、截图与剪贴板，各自的残余风险是什么？
- 密钥在内存中的生命周期：如何避免长期驻留？页面隐藏/退出时是否清除？
- 「用户被告知了什么」也要进威胁模型：不告知就是欺骗，过度承诺就是虚假安全。

**评审门槛**：以上四项形成一份独立文档，作为 `docs/architecture/adr/` 下的新 ADR
（建议标题「画像跨设备端到端加密同步」），
由技术负责人 + 至少一名未参与实现的成员审阅，并对「丢失恢复」与「威胁模型」两节逐条签字。
在此之前，任何 `POST /edu/skill-profile` 之类的接口、任何把自评数据写入 `edu_` 表的迁移脚本
都不接受合并。

## 备选方案（Alternatives considered）

| 方案 | 为什么没选 |
|---|---|
| **建 `edu_user_profile` 明文表** | 违反方案 ch.6.1；一旦入库就要配套字段级授权、导出审计、删除请求证明、脱敏与备份策略，MVP 团队规模撑不起；且「删除请求」本身难以证明已执行 |
| **服务端加密存储**（列级加密 + KMS） | 需要密钥管理、轮换、审计与「谁能解密」的授权模型；密钥在服务端意味着管理员/运维理论上可解密，隐私承诺从「不能」退化成「不承诺」 |
| **只用 `localStorage`** | 容量约 5 MB、同步 API 会阻塞主线程、不支持事务与索引、无法做结构化查询与版本迁移；Dexie/IndexedDB 的成本并没有比它高多少 |
| **直接上跨设备端到端同步** | 方案 ch.7.3 明确要求先评审四件事；在没有 SSO 身份锚点的阶段做同步，等于把账号安全风险叠加到画像上 |
| **画像只放内存（刷新即丢）** | 完全失去「学习记录」价值，产品上不可接受；且仍然要回答导出问题 |
| **把画像整个交给学校系统** | 数据所有权错位：自评与职业意向不属于学籍数据，学校系统也不提供这类字段 |
